00 · STARTStart here

You build agents in Python. The words around them, VM, Docker, CI/CD, virtual network, NSG, TLS, sound like a different job. They are not. Each one is a small idea with a scary name, and this guide takes them one at a time, using the real setup of agents_and_connectors as the worked example.

  • Draw, from memory, how a request travels from a browser to the database and back, and which fence it passes on the way.
  • Explain why the platform can deploy a new version without anyone noticing.
  • List what you need to put mini-agents on the internet, and in which order to set it up (section 13).

The mental model in one sentence

A VM is a computer you rent. Docker packs your app into a box that runs the same everywhere. Compose starts several boxes together. nginx is the one door into the machine. The network and firewall decide who can reach that door. The pipeline is a robot that tests your code and carries it to the machine every time you merge. Monitoring is how you find out it broke before a user does.

The whole thing in one picture

Left to right is how code moves. Bottom right is how people reach it. The VM is the only machine you operate yourself; everything else is rented by the minute or run by Microsoft.

You already know more than you think

Section 01

01 · THE BIG PICTUREWhat runs where

Before any single technology, get the layers straight: what is a machine, what is a box on the machine, what is a service Microsoft runs for you, and what is only a file that tells a robot what to do.

An analogy to hang everything on: a restaurant

  • The building you rent is the VM. You do not own it, you cannot touch it, but inside it you decide everything.
  • The kitchen stations are containers. Each has exactly the equipment it needs and nothing else; the pastry station does not have a grill. If one station burns down you rebuild that one.
  • The host at the door is nginx. Every guest passes the host, who checks the reservation, points them to a table, and turns strangers away.
  • The pantry is Postgres (and Redis for the sticky notes). Stations come and go; the pantry is what must survive.
  • The fence and the gates are the Azure network and its security group. Deliveries come through one gate, guests through another, and the back alley is closed.
  • The delivery truck is the pipeline. It brings the new menu, and the restaurant swaps it in while guests keep eating.
  • The suppliers are Azure services: the models (AI Foundry), the prediction endpoints (Azure ML), the warehouse (Azure SQL). The restaurant calls them; it does not run them.

In this project: why everything sits on one VM

docs/WIKI/Architecture.md gives the reasons: an internal audience with modest traffic, a small team that must be able to operate it, and Compose making any container replaceable on its own. Kubernetes or Azure Container Apps is a known later step, not a missing piece. This is the right instinct for your own projects too: one machine, a handful of containers, a pipeline covers more ground than most people expect.

Pitfall: confusing "a service" with "a machine"

When someone says "the backend is down" they mean the backend containers, not the VM. When they say "the VM is down" nothing on it answers, including nginx and the watchdog. The monitoring in section 11 is built around exactly this difference: each VM watches its own containers, and Azure watches the VM from outside.

Check yourself

Which pieces of this platform does the team operate themselves, and which does Microsoft run?

Themselves: the two VMs and the seven containers on each (nginx, backend, mcp-server, postgres, redis, worker, watchdog), plus the pipeline definition. Microsoft: AI Foundry (models), Azure ML endpoints, Azure SQL, Key Vault, Blob Storage, Application Insights, Entra sign-in, the pipeline's hosted build agents, and the physical hardware under the VMs.

Where does the model actually run when an agent answers?

Not on the VM. The backend container calls Azure AI Foundry over HTTPS; the VM only runs the orchestration around the call (prompt, tools, streaming the answer back).

What is the one difference between the dev VM and the prod VM in terms of configuration?

APP_ENV in each VM's .env. It selects the environments.dev or environments.prod block in config.yaml (vault, identity, sign-in app, URLs). Everything else in .env is a secret, not a setting.

Section 02

02 · THE MACHINEVirtual machines

A virtual machine is a computer you never see. You pick its size and operating system, Azure carves it out of a much bigger server, and you log into it over the network. Everything in this platform ultimately runs on two of them.

Physical, virtual, container, managed: four ways to run a program

WayWhat you getWhat you manageExample here
Physical machineA real box.Everything, including the hardware.Your laptop.
Virtual machineA slice of a big server, with its own OS, disk and IP.The OS and everything on it. Not the hardware.AZ-DEV-SV-MCP01, AZ-PRD-SV-MCP01.
ContainerA process in a box on a machine, with its own files and network view.What is in the box. The OS underneath belongs to the VM.The backend container (section 03).
Managed service (PaaS)A running thing behind an API.Nothing but your configuration and your bill.Azure AI Foundry, Key Vault, Azure SQL.

The trade is always the same: the further down the table, the less you can break and the less you can change. The team chose VMs because Docker Compose on a VM is simple to reason about, cheap, and lets them run anything (an ODBC driver, headless Chromium, Tesseract) without asking a platform for permission.

The words on a VM's spec sheet

  • Size: a name like Standard_B2as_v2. B is the burstable family (cheap, can sprint briefly), 2 is two vCPUs, a means AMD, s means it supports premium disks. Roughly: a modest two-core laptop that never sleeps.
  • Image: the operating system it starts from. Here Ubuntu 22.04 LTS, the most common choice for servers; "LTS" means it gets security updates for years.
  • OS disk: its hard drive. 128 GB standard SSD here. Docker images and Postgres live on it.
  • Region and zone: which data centre (westeurope, that is the Netherlands) and which building inside it (zone 1).
  • NIC and IPs: its network card, with a private IP inside the company network and, optionally, a public IP on the internet. Section 06.
  • Admin user and SSH key: how you log in. The user is tccadmin; password login is disabled, only an SSH key works.
  • Managed identity: the VM's own badge in Azure, so it can read Key Vault or Blob Storage without a password anywhere on disk. Section 07.

SSH: the way in

SSH is a secure remote terminal. You type on your laptop, the commands run on the VM. It uses a key pair: the public half sits on the VM in ~/.ssh/authorized_keys, the private half stays on your laptop and never leaves it. From the TCC network or the VPN:

# the dev VM, by its private IP
ssh tccadmin@172.16.126.36

# once there: where the code is, what is running
cd /home/code/agents_and_connectors
sudo docker compose ps

Keys beat passwords for one reason: a password can be guessed from anywhere on the internet, a 256-bit key cannot. The Bicep file that builds the prod VM sets disablePasswordAuthentication: true, so there is nothing to guess.

What a fresh VM needs before it can run the stack

A bare Ubuntu VM has no Docker and no git. infra/app-vm/cloud-init.yaml is the list of what the first boot installs; cloud-init is the standard way to run commands on a brand-new VM before anyone logs in:

#cloud-config
packages:
- ca-certificates
- curl
- git
- jq
- postgresql-client
runcmd:
- curl -fsSL https://get.docker.com | sh        # Docker + Compose
- usermod -aG docker tccadmin                  # let the admin run docker
- curl -sL https://aka.ms/InstallAzureCLIDeb | bash   # the az command
- install -d -o tccadmin -g tccadmin /home/code # where the repo will go

What cloud-init deliberately does not do: clone the repo, write .env, copy the TLS certificate, or register the pipeline agent. Those need credentials, and a file checked into git must never carry credentials. They are the runbook's manual steps in infra/app-vm/README.md.

What keeps it running after a reboot

Two things. Docker itself starts at boot as a system service. Then infra/systemd/mcp-stack.service tells systemd (Linux's service manager) to run docker compose up -d in the repo folder once Docker is up. On top of that, every container in docker-compose.yml has restart: unless-stopped, so Docker restarts a crashed container on its own.

# a systemd unit is a small ini file: what to run, when, where
[Unit]
After=docker.service
Requires=docker.service

[Service]
Type=oneshot
RemainAfterExit=yes
WorkingDirectory=/home/code/agents_and_connectors
ExecStart=/usr/bin/docker compose up -d
ExecStop=/usr/bin/docker compose down

[Install]
WantedBy=multi-user.target   # "start at normal boot"

What the VM does not do

It does not run the language models (AI Foundry does). It does not hold the data warehouse (Azure SQL does). It does not store secrets as its main copy (Key Vault does). It runs the application, its database, its cache and its front door, and it calls everything else over HTTPS. That is why a two-core machine is enough.

Pitfall: pets and cattle

A server you set up by hand is a pet: unique, and nobody remembers what was done to it. The dev VM started that way. A server built from a file is cattle: lose it, run the script, get an identical one. The move from one to the other is exactly what infra/app-vm/ did for prod. Whenever you type something on a server, write it down somewhere in the repo the same day.

For your own project

One small Linux VM is plenty for a hobby agent app. Two vCPUs and 4 GB of RAM run Postgres, a Python API and a reverse proxy comfortably; 1 GB gets tight once Postgres and a build run at the same time. Pick Ubuntu LTS, log in with an SSH key only, and install Docker with the same one-liner this project uses.

Check yourself

Why does the prod VM refuse password logins?

A password can be brute-forced from anywhere that can reach port 22. An SSH key cannot be guessed, and its private half never leaves your laptop. Disabling password authentication removes the whole attack.

Why are the repo clone, .env and the certificate not in cloud-init.yaml?

They need credentials or are credentials (a token to clone, the secrets in .env, the private key of the certificate). cloud-init.yaml is committed to git, so it may only contain things that are safe for anyone with repo access to read.

The VM reboots at 3 am. What brings the application back, in order?

Docker starts as a system service; the mcp-stack systemd unit then runs docker compose up -d in the repo folder; each container's restart: unless-stopped policy also brings back anything that was running before the reboot.

Section 03

03 · PACKAGINGDocker: images and containers

"It works on my machine" is the oldest problem in software. Docker solves it by shipping the machine along with the code: a frozen filesystem with Python, the libraries, the system packages and your source, that runs identically on your laptop, in CI and on the VM.

Image versus container

  • An image is a read-only snapshot: a Linux filesystem with everything your app needs, built once from a recipe called a Dockerfile. Think of a frozen ready meal with the cooking instructions printed on it.
  • A container is one running copy of an image: a normal Linux process, given its own view of the filesystem, its own network address and its own hostname. The meal being heated and eaten. You can heat two from the same box at the same time; this project runs two backend containers from one image.
  • A volume is a folder that lives outside the container, so it survives when the container is thrown away. Postgres's data directory is a volume; the container is disposable, the data is not.
  • A port publish (-p 8000:8000) connects a port on the machine to a port inside the container. Without it, nothing outside can talk to the process.

Images are built in layers, one per Dockerfile instruction, and each layer is cached. Order the Dockerfile so that what changes rarely (installing dependencies) comes before what changes often (copying your source), and rebuilds take seconds instead of minutes.

Read the real Dockerfile

backend.Dockerfile is a multi-stage build: three temporary images, of which only the last one ships. Here it is, abridged, with the reasons the comments in the file give:

# ── Stage 1: install Python dependencies ───────────────────────────
FROM python:3.12-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:0.12 /uv /uvx /bin/     # bring in uv
WORKDIR /app
RUN --mount=type=bind,source=uv.lock,target=uv.lock \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    uv sync --locked --no-install-project --no-dev
# --locked: fail if uv.lock disagrees with pyproject.toml. Never re-resolve in a build.

# ── Stage 2: build the React app ───────────────────────────────────
FROM node:22-alpine AS frontend
WORKDIR /app
COPY chatkit/package.json chatkit/pnpm-lock.yaml ...   # manifests first: cache
RUN pnpm install --frozen-lockfile --ignore-scripts
COPY chatkit/ ./
RUN pnpm --filter campaign-forecasting-app build         # → /app/app/dist

# ── Stage 3: the image that ships ──────────────────────────────────
FROM python:3.12-slim AS production
WORKDIR /app
RUN groupadd --gid 1000 appgroup \
    && useradd --uid 1000 --gid appgroup --create-home appuser   # non-root
RUN apt-get install ... curl libgomp1 tesseract-ocr msodbcsql18   # OS packages
COPY --from=builder /app/.venv /app/.venv          # the dependencies, nothing else
ENV PATH="/app/.venv/bin:$PATH"
RUN python -m playwright install --with-deps chromium   # for the Slides export
COPY --chown=appuser:appgroup src/ ./src/
COPY --chown=appuser:appgroup config.yaml auth/ ...
COPY --from=frontend --chown=appuser:appgroup /app/app/dist ./frontend/
USER appuser
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=10s --retries=3 \
    CMD curl -f http://localhost:8000/api/health || exit 1
CMD ["fastapi", "run", "--entrypoint", "src.api.chatkit_server:app", "--port", "8000"]

Why each decision

DecisionReason
Three stagesThe build tools (uv's cache, node, pnpm, the npm packages) never reach the final image. Smaller image, less to attack, faster to start.
Install from the lock fileuv sync --locked installs exactly the versions in uv.lock. The image you tested is the image you ship. If the lock is stale, the build fails instead of quietly picking newer versions.
Manifests before sourceCopying pyproject.toml and the lock first means the slow dependency layer is cached until they change. A code-only change rebuilds in seconds.
Non-root user (uid 1000)If the app is ever compromised, the attacker is an unprivileged user inside a container, not root on the VM. This uid matters again in section 10: files the container writes must be owned by it.
HEALTHCHECKDocker calls /api/health every 30 s and marks the container healthy or unhealthy. Compose, nginx and the deploy script all rely on that status.
One process per containerThe comment on the CMD explains it: with one process, a stop signal closes the port immediately and nginx moves on to the other replica. A multi-worker server kept the port open and queued requests nobody answered. Compose runs two containers instead of one container with two workers.

In this project: one image, four jobs

The backend, the MCP server, the worker and the watchdog all run the same image; Compose gives each a different command (uvicorn src.api.mcp_server:app, python -m src.tasks.worker, python -m src.ops.watchdog). One build, one set of dependencies to keep in sync, one thing to test. Pitfall: who owns the folder

When a container mounts a host folder that does not exist yet, Docker creates it as root. The container runs as uid 1000, so it then cannot write there. This happened for real: data/recast shipped without being pre-created, Docker made it as root, and every reCAST reprojection failed with "Permission denied" until the deploy script learned to create the folder with the right owner first. Section 10 shows where.

Check yourself

What is the difference between an image and a container, in one sentence each?

An image is a frozen, read-only filesystem built from a Dockerfile. A container is one running process started from that image, with its own writable layer, network address and hostname.

Why copy pyproject.toml and uv.lock before copying src/?

Layer caching. The dependency install layer is rebuilt only when those two files change. If the source were copied first, every code change would invalidate the cache and reinstall every package.

You edit pyproject.toml to add a package but forget to run uv lock. What happens to the Docker build?

It fails. uv sync --locked refuses to run when the lock file no longer matches pyproject.toml. That is a feature: the alternative is an image with versions nobody chose.

Section 04

04 · ORCHESTRATIONDocker Compose: many containers, one file

A real application is several processes: a database, a cache, the API, a background worker, a proxy. Compose describes them all in one YAML file, starts them in the right order on a private network, and restarts the ones that fall over.

The backend service, annotated

backend:
  build:
    context: .
    dockerfile: backend.Dockerfile
  deploy:
    replicas: 2                 # two containers, no container_name, no host port:
                                # nginx finds both through Docker's DNS (section 05)
  stop_grace_period: 180s       # let a streamed answer finish when a deploy retires this copy
  env_file:
  - path: .env
    required: false             # on the VM secrets come from Key Vault instead
  volumes:
  - ./data/uploads:/app/data/uploads        # user files, outside the container
  - ./data/sessions:/app/data/sessions
  - ./skills:/app/skills:ro                 # :ro = read-only
  environment:
    DATABASE_URL: postgresql+asyncpg://postgres:postgres@postgres:5432/chatkit
    APP_VERSION: ${APP_VERSION:-dev}        # the commit, set by deploy.sh
  depends_on:
    postgres: { condition: service_healthy }
    redis:    { condition: service_healthy }
  healthcheck:
    test: [CMD, curl, -f, http://localhost:8000/api/health]
    interval: 30s
    start_period: 90s           # time to boot before failures count
    start_interval: 2s          # but check often, so a new replica takes traffic fast
    retries: 3
  restart: unless-stopped
  networks:
  - agent-network

Notice what is not there: no ports. The backend is unreachable from the VM's network card. Only nginx, on the same private Docker network, can call it. That is the single most important line in the file, and it is a line that is missing.

The private network

Compose creates a virtual switch (agent-network, driver bridge) and plugs every container into it. On that network, service names are hostnames: postgres, redis, backend, mcp-server. When a service has two replicas, its name resolves to both addresses, which is how nginx load-balances without being told anything. This traffic never leaves the VM.

What survives, what does not

  • Named volumes survive docker compose down and image rebuilds: chatkit-postgres18-data (the database), agent-redis-data. They die only with down -v or docker volume rm.
  • Bind mounts are ordinary folders in the repo checkout: data/uploads, data/sessions, data/presentations, data/recast, data/ops, data/backups. Git ignores them; a deploy must not delete them.
  • Everything else inside a container is gone when the container is replaced. If your code writes a file somewhere that is not a mount, the next deploy erases it.

Pitfall: one colon changes everything

Beginners write the second form because tutorials do. This project writes the first.

Check yourself

Why does the backend service have neither a container_name nor a ports entry?

Two replicas cannot share one fixed name, and a deploy starts the new copies next to the old ones before stopping anything, so there are briefly four. A published host port could be bound by only one of them. nginx reaches all of them by DNS on the private network instead.

What does condition: service_healthy buy over plain depends_on?

Plain depends_on waits for the container to start; Postgres takes a few seconds more to accept connections. With the health condition the backend starts only once pg_isready succeeds, so it does not crash on its first query.

Which data would docker compose down -v destroy on the VM, and which would it leave?

Destroy: the Postgres database and Redis (named volumes). Leave: uploads, sessions, presentations, backups and the other bind-mounted folders under data/, which are ordinary folders on the VM's disk.

Section 05

05 · THE FRONT DOORnginx: the reverse proxy

Every request to the platform, from a browser or from another agent platform, lands on nginx first. It holds the HTTPS certificate, decides whether the caller may come in at all, and forwards the request to the right container. Understanding it is understanding most of the network and security story.

What a reverse proxy is

A proxy sits between a client and a server and forwards traffic. A reverse proxy sits in front of your servers and faces the world: clients talk to it and never to the servers behind it. Four things you get from that one extra hop:

  • TLS termination: the proxy speaks HTTPS to the outside and plain HTTP to the containers. Your Python code never touches a certificate.
  • Routing: one hostname, one port 443, many services behind it, chosen by path (/api/ to the backend, /mcp to the MCP server).
  • Load balancing and resilience: two backend replicas behind one name; if one refuses a connection the proxy tries the other.
  • Policy at the edge: allow-lists by source address, security headers, size limits, timeouts, before any application code runs.

The shape of nginx-proxy.conf

An nginx file is a tree of blocks. http holds global settings and several server blocks; each server block answers one hostname on one port and holds location blocks that match paths. This project's file (infra/nginx/nginx-proxy.conf) has four server blocks:

Before any route is chosen, two geo tables classify the caller by IP address, and a map decides whether the request is allowed on the public side:

    10.0.0.0/8     1;

# anyone else: 404 before a location is even chosen.
if ($edge_ok = 0) { return 404; }

This is default deny: a new backend route stays closed to the outside until someone lists it. The comments in the file record the day DevRev's egress addresses were measured and why only one is listed. That is good engineering writing: the config explains the decision, not just the setting.

How nginx finds two replicas without being told

resolver 127.0.0.11 valid=10s ipv6=off;   # Docker's DNS, re-asked every 10 s
proxy_connect_timeout 2s;                  # a replica that just left: give up fast, try the next

127.0.0.11 is Docker's internal DNS server. Asking it for backend returns every running replica's address. Because nginx re-asks every ten seconds, a deploy can start new replicas and retire old ones and nginx simply follows. This single setting is what makes zero-downtime deploys (section 10) possible without any load balancer.

Security headers and limits

Every response from the HTTPS server carries headers that tell browsers how to behave: Strict-Transport-Security (always use HTTPS for a year), X-Frame-Options: DENY and Content-Security-Policy: frame-ancestors 'none' (nobody may embed the site in an iframe), X-Content-Type-Options: nosniff, Referrer-Policy, Permissions-Policy. Plus client_max_body_size 50m so uploads work and anything bigger is refused at the door.

Certificates

HTTPS needs a certificate that proves the server is who it says. Here it is the company's wildcard certificate for *.tccglobal.com, two files (.pem public part, .key private part) placed by hand in certs/ on each VM, git-ignored, mode 600, and mounted read-only into the nginx container. The watchdog warns 21 days before it expires. For your own project you will not have a corporate wildcard; section 13 uses Let's Encrypt, which issues free certificates automatically.

In this project: the config is a mounted folder, not a baked file

Compose mounts ./infra/nginx as a folder into the container. A deploy's git reset replaces the file in that folder, nginx tests the new config (nginx -t), and only if the file's hash changed does it reload (nginx -s reload). The container itself is not recreated, which matters because a reload can drop one connection in about 700 that is mid-handshake, so the deploy avoids reloading when nothing changed.

Pitfall: the address nginx sees

The allow-lists use $remote_addr, the address of whoever connected to nginx. That is correct only while nginx is the edge. Put a load balancer or a CDN in front and every request arrives from the load balancer's address: the lists would admit everyone or no one. The file says so in a comment, because the person who adds a load balancer in two years needs to read it.

Check yourself

What does "TLS termination" mean, and why is it convenient?

nginx decrypts HTTPS and talks plain HTTP to the containers on the private network. The application code never handles certificates, and one certificate serves every service behind the proxy.

A request arrives on 443 with the hostname evil.example.com pointed at the VM's IP. What happens?

No server block has that server_name, so the default server for 443 answers: return 444, which closes the connection without a response.

Why can a deploy add and remove backend containers without editing the nginx config?

The config names the service (backend), not addresses, and re-resolves the name through Docker's DNS every 10 s. New replicas appear in the answer; stopped ones disappear, and a 2 s connect timeout skips one that just left.

The journey of one request

Three checkpoints, each owned by a different layer: Azure (NSG), nginx (edge rules), the application (session or token). Each assumes the one before it might be misconfigured.

  1. The browser asks DNS for chat.tccglobal.com. On the company network it gets the private IP; from the internet it gets the public one.
  2. The packet reaches Azure. The NSG attached to the VM's network card checks: source address, destination port 443, protocol TCP. A rule matches (TCC ranges, or DevRev's single address) or the default DenyAllInBound drops it silently. A blocked caller sees a timeout, not an error page.
  3. nginx accepts the TCP connection on 443, completes the TLS handshake with the wildcard certificate, and runs the edge rules from section 05: internal caller, DevRev on an allowed path, or 404.
  4. nginx forwards to backend:8000 over the Docker bridge network. The backend's Python middleware checks the session token.
  5. The backend talks to postgres:5432 on the same private network, and to Azure services over outbound HTTPS.
  6. The answer streams back the same way, through nginx, with the security headers added.

Check yourself

Why does the dev VM have a public IP at all if the site is internal?

DevRev's agent platform calls the dev instance's A2A and MCP endpoints from the internet. The NSG admits only DevRev's address, only on 443, and nginx then admits only the A2A and MCP paths.

Someone on the internet scans the prod public IP on port 5432. Name the two things that stop them.

A VNet is the private network inside Azure where the VM's private address lives. A VPN is a tunnel that puts a remote laptop inside that private network so it can use those addresses. One is a place, the other is a road into it.

Section 07

07 · SECURITYLayers, identities and secrets

Security is not one feature; it is a habit applied at every layer. This section names the habits (defence in depth, least privilege, no secrets in git, fail closed, know who did what) and shows where each one lives in this platform.

Five habits

  • Defence in depth: several independent fences, so one mistake is not a breach. The NSG, nginx and the application each check on their own.
  • Least privilege: every process and person gets the minimum. Containers run as an unprivileged user; a signed-in person sees only the agents and warehouse rows granted to them; the default for an unknown person is no agents.
  • No secrets in git: .env and certs/ are ignored; a pre-commit hook refuses commits containing private keys; CI sets KV_DISABLED=1 so a test run can never read the real vault.
  • Fail closed: when a check cannot be made, refuse. A person whose warehouse token cannot be renewed is refused rather than silently promoted to the service identity.
  • Audit: requests are logged with address, path, status and latency; warehouse reads run as the person so the database audit names them; every change made through the ops tool is written to an audit table with the caller's name.

Authentication versus authorization

Two words that beginners merge. Authentication answers "who are you?"; authorization answers "what may you do?". On the /mcp endpoint: a valid Entra token proves who is calling (authentication); the token's group claims are mapped to a role in auth/group_roles.json, and auth/skill_roles.json says which role may consult which agent (authorization). Anyone in the company tenant can authenticate; most are then refused with 403 no_role. Authenticated is not the same as allowed.

Managed identity: a badge instead of a password

The classic way to let a server read a vault is to give it a password, which then has to be stored somewhere on the server, which is the problem you were trying to solve. Azure's answer is the managed identity: the VM has an identity of its own in Entra (AZ-DEV-SV-MCP-ID-01, AZ-PRD-SV-MCP-ID-01). Azure services grant rights to that identity (Key Vault: Secrets User; Blob Storage: Blob Data Reader; Azure SQL: a database user). When the app needs a token it asks a local Azure endpoint, which knows which VM is asking. No password exists anywhere. The code in src/config.py tries the managed identity first, then falls back to whatever az login provided on a laptop, then to .env.

HTTPS, in two sentences

TLS encrypts the connection so nobody between the browser and nginx can read or change it, and the certificate proves the server is really chat.tccglobal.com. nginx refuses TLS 1.0 and 1.1 (old, broken) and tells browsers via HSTS to never try plain HTTP again.

Known gaps, stated honestly

  • CORS is allow_origins=["*"], so any website could call the API (with the user's own token, not without it).
  • The MCP_RATE_LIMIT variable in the compose file is not read by the code; rate limiting exists in src/api/rate_limit.py, keyed on the real client address, but that variable is dead.
  • Pull requests are not validated by CI before merge (section 09), so the pre-commit hooks are the only check before code lands on dev.
  • Model-written transform scripts run inside the backend process with restricted builtins: a guard, not a sandbox. Isolating them in their own container is an open item.

A security page that lists its own gaps is worth more than one that claims perfection. Keep that habit in your own projects.

In this project: why "fail closed" was learned the hard way

The warehouse client used to fall back to the VM's service identity when a person's token was missing on one of the two backend replicas. Result: that person briefly saw every client's data with the service identity's rights. The fix was to refuse instead, and to offer a one-click reconnect in the UI. A silent fallback that "makes it work" is often a security bug wearing a helpful face.

Pitfalls beginners make, all seen in the wild
  • A token in the URL (?api_key=...): it lands in every access log. The old middleware accepted that; the new one does not.
  • Default allow: giving every signed-in person one agent "so the page is not empty". This platform's default is now no agents and a request-access page.
  • Committing .env once. Git never forgets; the secret must be rotated, not just deleted.
  • Running containers as root because the tutorial did.

Check yourself

Explain authentication versus authorization using the /mcp endpoint.

Authentication: the Entra token's signature, audience and issuer are verified, so the server knows which account is calling. Authorization: the token's groups map to a role, and the role must be allowed for the requested agent. A valid token with no mapped group is authenticated but refused.

Why is a managed identity safer than a key in .env?

There is nothing to steal from disk and nothing to rotate: Azure issues short-lived tokens to the VM because it knows which VM is asking. A key in a file can be copied, leaked into a log, or committed.

Why does the Postgres password in docker-compose.yml not matter today, and when would it?

Postgres listens on 127.0.0.1 only and nothing outside the VM can reach it, so the password protects against nothing the network does not already stop. It would matter the moment the port were published on all interfaces or Postgres moved to a managed service.

Section 08

08 · CONFIGURATIONEnvironments and configuration

"Local, dev, prod" is the simplest promotion ladder there is: your laptop, a test copy that real colleagues use, and the real thing. The discipline that makes it work is one rule about where settings live.

Why three environments

local

Fast and forgiving

Hot reload, no login, Key Vault unreachable so secrets come from .env. Break it as often as you like.

dev

Real, but not for customers

Same containers, same sign-in, same warehouse as prod. Where testers try a feature before it is released. Deployed on every merge to dev.

prod

The real thing

Deployed on every merge to main. A release is a reviewed pull request from dev to main; rollback is reverting it.

The value of dev is that a mistake is found by a colleague on a test site, not by a project manager during a client call. The cost is a second VM and the discipline to keep both identical except for what must differ.

The one rule

From the project's CLAUDE.md

APP_ENV (local | dev | prod) is the only setting that differs per environment in .env; everything else in .env is a secret. Non-secret settings live in config.yaml, and a value that differs per environment goes under environments.<env> there, never in .env.

Why so strict? Because .env is invisible: git-ignored, different on every machine, never reviewed. If a setting lives there, nobody can see in a pull request that dev and prod differ. Keeping every non-secret in config.yaml means the difference between environments is a reviewable diff in the repo:

# config.yaml, sketched
keyvault:
  url: https://AZ-DEV-SV-MCP-KV-01.vault.azure.net/
environments:
  prod:
    keyvault:
      url: https://AZ-PRD-SV-MCP-KV-01.vault.azure.net/
    azure_ad:
      redirect_uri: https://chat.tccglobal.com/api/auth/azure/callback
    # ... the prod identity, sign-in app, model resource

src/config.py reads APP_ENV and merges that block over the defaults. One switch, one place.

How a secret is resolved

  1. Key Vault, if keyvault.url is set and KV_DISABLED is not. First with the VM's managed identity, then with whatever az login provides on a laptop.
  2. The environment variable from .env.
  3. The default in config.yaml, if there is one.

On a laptop, step 1 usually fails politely (the vault's firewall refuses your home address) and step 2 wins. scripts/fetch_env.ps1 fills a laptop's .env from the vault when you are on the office network. A secret that falls back from vault to .env on a VM is reported as a degraded mode, so it shows in the admin console rather than being forgotten.

The twelve-factor idea, in one paragraph

A well-known checklist for web apps ("The Twelve-Factor App") says: keep config in the environment, not in code; build once and run the same build everywhere; treat backing services (database, cache, model API) as attached resources named by a URL. This project follows the spirit: one image, config by APP_ENV, backing services by URL. It bends one rule: the image is rebuilt on each VM rather than built once and shipped, which is simpler but means a build can differ by a dependency that moved between the two builds. The lock file is what keeps that from happening.

In this project: the default that bites

APP_ENV defaults to prod. A dev VM whose .env lacks the line would quietly read prod's vault and sign people in with prod's app. The wiki's Deployment page says to set it before the first deploy. Defaults should be the safe choice; here the safe choice was "behave like prod" for the running site, at the cost of this trap for a new VM. Know the trade-off you are making when you pick a default.

Pitfall: personal overrides

If only your laptop needs a different model endpoint, it belongs in the git-ignored config.local.yaml (there is an example file), which is merged only when APP_ENV=local. Never in config.yaml, which ships to prod, and never in .env, which is for secrets.

Check yourself

A colleague adds FOUNDRY_ENDPOINT=https://... to the VM's .env because prod needs a different one. What is wrong with that?

It is not a secret, so it does not belong in .env; the difference is now invisible to reviewers and will be lost when the VM is rebuilt. It belongs under environments.prod in config.yaml.

Why does the same secret work on the VM but not on your laptop, even though you ran az login?

Key Vault's firewall admits only the VM's subnet and the office addresses; from home through the split-tunnel VPN your traffic still leaves from your home IP. The laptop falls back to .env, which may not have that key yet.

What is a release in this project, mechanically?

A pull request merging dev into main. The pipeline then deploys main to the prod VM. Rolling back is reverting that merge; the data is untouched.

What each job is for

  • PythonChecks: ruff catches style and real bugs (unused variables, bad imports); ruff format --check refuses unformatted code; bandit flags risky patterns (shell injection, hard-coded passwords).
  • PythonTests: the hermetic tests, with the authentication tests run first and alone because they are the security boundary and they finish in seconds. Tests marked integration (they call the live warehouse, Azure ML or a model) are skipped here on purpose.
  • FrontendBuild: builds the React app with the exact pnpm version pinned, and runs its unit tests.
  • DockerBuild: builds the image and throws it away. It exists only to catch a Dockerfile that stopped building, before the VM finds out during a deploy.

What "hosted agent" means in practice

Microsoft starts a clean Ubuntu VM, checks out your repo, runs your steps, uploads the logs and destroys the VM. Nothing persists; nothing of yours is installed; it cannot reach your VMs or your vault unless you give it credentials. That isolation is why KV_DISABLED=1 matters: hosted agents are Azure VMs, and without the switch a stray credential could have resolved production secrets during test collection.

The honest gotcha: PRs are not validated

Measured, not assumed

The YAML has a pr: block, and it does nothing. Azure Repos ignores the YAML pr trigger; pull-request validation there comes from a branch policy, and no branch carries one. So the checks run after a merge, not before. A failing ruff blocks the deploy, not the merge. That is why the project's rules say to run what CI runs before opening a PR, and why pre-commit hooks exist. The comment in the YAML records the date this was measured.

On GitHub, which is where mini-agents lives, on: pull_request genuinely runs before merge, and branch protection can refuse the merge button until the checks pass. Section 13 sets that up.

Check yourself

Why run the tests on a Microsoft VM rather than on the dev VM, which already has everything installed?

A fresh machine proves the repo is self-contained (the lock file, the Dockerfile, the pinned tool versions). The dev VM has state, secrets and traffic; a test suite should have none of those. And four jobs run in parallel on four hosted machines, which the two-core dev VM could not do.

A merge to dev fails ruff format --check. What is the user-visible effect?

None, immediately: the code is already merged. The CI stage fails, so the DeployDev stage does not run, and the dev site keeps serving the previous version until someone fixes the formatting and merges again.

Why are integration tests excluded from CI?

They call live services (the warehouse, Azure ML endpoints, models) that cost money, need credentials the hosted agent must not have, and can fail for reasons unrelated to the code change.

Section 10

10 · DELIVERYCD: how code reaches the VM

Continuous deployment is the second half of the pipeline: once the checks pass, the same run puts the code on the machine. This project does it with a script on the VM that replaces the running containers one service at a time, without a second of downtime. It is the most sophisticated part of the platform and the one most worth understanding.

Two ways to deploy to a machine

  • Push: the pipeline runner opens an SSH connection to the VM and runs commands. Simple; the runner needs an SSH key to the server.
  • Agent on the machine: a small program on the VM registers with the pipeline service and waits; the pipeline hands it the job. The VM needs no inbound access from the runner, and the pipeline needs no key to the VM.

This project uses the second. In Azure DevOps it is called an environment with a VirtualMachine resource: an agent installed on each VM, registered to the environment named dev or prod. The deployment job then literally runs on the VM, in the agent's own checkout of the repo. Because that checkout is made with the pipeline's temporary job token, the VM never stores a personal access token.

- stage: DeployDev
  dependsOn: CI
  condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/dev'))
  jobs:
  - deployment: DeployToVM
    environment:
      name: dev                    # the ADO environment the dev VM's agent registered with
      resourceType: VirtualMachine
    strategy:
      runOnce:
        deploy:
          steps:
          - checkout: self
          - script: |
              chmod +x scripts/deploy.sh
              scripts/deploy.sh      # runs ON the VM

- stage: DeployProd                # identical, for main → environment prod

What deploy.sh does, in order

  1. Take the code. Reset the repo at /home/code/agents_and_connectors to the commit the pipeline checked out; the branch comes from the pipeline (BUILD_SOURCEBRANCHNAME). APP_VERSION becomes the short commit hash, so every container can say which version it is.
  2. Tell the watchdog. Write data/ops/deploy.json; while a deploy runs, and for two minutes after, failures are recorded but open no incident, so a deploy does not page anyone.
  3. Prepare the folders. Create every bind-mounted data/* folder and give it to uid 1000 (the container user) with the admin's group. This is the fix for the "Docker created it as root" pitfall from section 03.
  4. Build the images while the old containers keep serving. About six minutes.
  5. Back up the database: a pg_dump into data/backups, keeping the last ten. If this fails, nothing has been stopped yet.
  6. Refresh the host timers (section 11) if their unit files changed.
  7. One-time migrations (the Postgres 15 to 18 move), harmless once done; then up -d for Postgres and Redis only, which recreates them only if their own definition changed.
  8. Roll out the backend, then the MCP server, with rollout.sh (below). This is the no-downtime part.
  9. Drain and replace the worker: it gets up to 150 s to finish the upload it is parsing; queued uploads simply wait. Replace the watchdog.
  10. nginx: test the config inside the container; reload only if the file's hash changed.
  11. Start anything new in the compose file that is not running yet, without recreating what is.
  12. Health checks from inside the containers (no service has a host port). If anything failed along the way, dump container state and the last 120 log lines into the pipeline log, so a failed deploy explains itself.

The start-first rollout

scripts/rollout.sh replaces one service's containers the way Docker Swarm and Kubernetes do it: the new ones start next to the old ones and have to earn their place.

nginx sees all four through Docker's DNS during the overlap. A stopped old container closes its port at once; nginx retries that request on another replica.

The gates, in order:

  1. Healthy. Each new container must pass its Docker healthcheck within 240 s. Exited, dead or unhealthy means rollback.
  2. Self-test (backend only). Each container runs a startup self-test (python -m src.ops selftest) that lists what it is missing. The new container may not add a problem the old one did not have; a version that comes up without something it needs never replaces the running one.
  3. Canary. Old and new serve real traffic together for 45 s. The host collector reads nginx's access log and compares errors per replica. If the new ones fail more requests than the old ones, rollback.
  4. Retire the old. docker stop with a grace period: the stop signal closes the port immediately, nginx sends new requests elsewhere, and the old container has up to 180 s to finish the chats it is still streaming.

Why it works, and would not work without each piece: nginx re-resolves the service name every 10 s (section 05); the services have no fixed container name and no host port (section 04); every container has a healthcheck (section 03); and each container is one process, so closing the port is instant.

Rollback

Revert the merge on the branch. The pipeline deploys the previous commit the same way. The database and Redis are untouched. One rule follows from the overlap: for about a minute the old and the new version run against the same database, so a schema change may only add tables and columns; drop or rename in a later release.

In this project: the simplest possible deploy, for comparison 
ssh vm 'cd /home/code/app && git pull && docker compose up -d --build'

That one line is what most hobby projects need and it is roughly what this project did before rollout.sh existed: a few seconds of downtime while containers restart. Everything in deploy.sh beyond that line exists for a reason that was felt: the backup because a migration once had to be rehearsed; the folder ownership because of data/recast; the self-test gate because a container once came up without what it needed; the canary because "healthy" does not mean "answers correctly". Start with the one line. Add each piece when you feel its reason.

Pitfall: building on the machine that serves

Building the image on the two-core VM takes six minutes and competes with live traffic. The common alternative is to build in CI, push the image to a registry (Azure Container Registry, GitHub's ghcr.io), and have the VM only pull: seconds instead of minutes, and the exact image that was tested is what runs. This project builds on the VM to stay simple; know that the other option exists.

Check yourself

Where does the deployment job run, and why does that matter for credentials?

On the VM itself, through the agent registered with the ADO environment. The pipeline's job token makes the checkout, so the VM holds no personal access token, and nothing needs SSH access into the VM from outside.

Name the three gates a new backend container passes before an old one stops.

Its Docker healthcheck; the startup self-test must add no new problem compared with the old container; the 45 s canary on nginx's access log must show it failing no more requests than the old ones.

A new version renames a database column. Why is that forbidden here, and what should happen instead?

During the overlap the old containers still run queries with the old column name against the same database and would fail. Add the new column in this release, make the code use it, and drop the old one in a later release.

Why the host collector exists at all

Some things only the host can see or do: which containers restarted, whether one was killed for memory, restarting an unhealthy one, running pg_dump against the volume, pruning Docker. The usual shortcut is to give a monitoring container the Docker socket, which is root on the host in disguise: any bug in that container owns the machine. This platform refuses that: a plain Python script, run by systemd timers as root outside every container, writes what it sees to a JSON file, and the watchdog container reads the file read-only. No container holds the socket. That is least privilege applied to monitoring.

# on the VM
systemctl list-timers 'tcc-ops*'          # the three timers and their next run
journalctl -u tcc-ops@collect -n 50       # the collector's log
jq . data/ops/host.json                   # what it saw last minute

Degraded modes: fallbacks that speak up

A quiet rule in the code: anything that carries on without something it needs (a guide file missing, a secret that fell back from Key Vault to .env, a sync that failed) calls degraded(code, detail, impact=...) instead of merely logging a warning, and recovered(code) when it works again. The watchdog turns every active degraded mode into an incident. The same self-test gates deploys (section 10). A warning in a log that nobody reads is not monitoring; an incident in a console with a runbook is.

Pitfalls
  • Monitoring only from the inside. A watchdog on the VM cannot tell you the VM is gone. The external alert on the heartbeat exists for that case.
  • Alerts that cry wolf. One failing probe opens nothing here; incidents need N failures in a row and resolve after N passes. An alert that fires every day gets muted, and then the real one is missed.
  • No backup is a backup until you restored from it. The Postgres 15 to 18 migration was rehearsed on copies before the deploy. Do a restore drill once.
For your own project, in this order
  1. A /health endpoint that checks the database, and a Docker healthcheck that calls it. restart: unless-stopped.
  2. A free external uptime checker (any of the well-known ones) pinging /health every minute from the internet and emailing you. This is your "Azure watches from outside".
  3. A daily backup by cron (pg_dump, or copy the SQLite file), kept for a week, restored once to prove it works.
  4. Logs you can read: docker compose logs is enough until you have users.
  5. Later: a disk-space alert, tracing of each agent turn, incidents with runbooks.

Check yourself

Why does no container get the Docker socket, and what does the platform do instead?

The socket is root on the host; a bug in that container would own the VM. Instead, a script run by systemd timers as root outside the containers records host and container state to a JSON file, and the watchdog reads it read-only.

The VM loses power. Walk through how someone finds out.

The watchdog stops logging its heartbeat to Application Insights; after 10 minutes the heartbeat alert fires an email. In parallel Azure's own VM availability metric drops and that alert fires within about 5 minutes. Nothing on the VM is involved, which is the point.

What is the difference between a log warning and a degraded mode here?

A warning sits in a log until someone reads it. A degraded mode is recorded by the code, becomes an incident in the watchdog, shows in the console with its impact and runbook, emails if critical or warning, and blocks a deploy if it is new in the new version.

12 · INFRASTRUCTUREInfrastructure as code

Clicking a VM together in the Azure portal works once. Writing it down as a file means you can review it, rebuild it, and make a second one that is identical. The file is the documentation, and it cannot drift from reality because it is what created reality.

The idea

You describe the resources you want (a VM of this size, a firewall with these rules, a vault with this policy) in a declarative file. A tool compares the file with what exists and creates, changes or deletes only the difference. Running it twice changes nothing the second time; that property is called idempotent, and it is what makes the file safe to re-run after every edit. On Azure the native language is Bicep; Terraform does the same across clouds. The ideas transfer one-to-one.

Two commands matter. what-if shows the diff before touching anything: a line per resource, marked create, modify or delete. deploy applies it. The project's scripts default to what-if, so the dangerous action takes a deliberate word.

Read a piece of the real Bicep

For your own project

Start in the portal if you must, but the moment it works, export it or rewrite it as a Bicep or Terraform file of one VM, one NSG and one public IP (under 100 lines), and delete and recreate the VM from the file once. Check yourself

What does idempotent mean for an infrastructure tool, and why do you want it?

Applying the same file twice leaves the second run with nothing to do. You can re-run after every edit without fear of duplicating or breaking resources, and the file stays the truth about what exists.

Why is the subnet a parameter rather than a resource in main.bicep?

The network belongs to IT and already exists; the VM must join it, not create a new one. Taking its id as input keeps the file's responsibility to what the team owns.

Why apply a Foundry change before merging the config.yaml that uses it?

A merge to main deploys prod at once. If the config names a model deployment that does not exist yet, prod would ship broken. Infrastructure first, then the code that depends on it.

  • Build in CI, pull on the VM. Push the image to ghcr.io from the workflow; the deploy becomes docker compose pull && docker compose up -d in seconds, and the tested image is the running image.
  • Postgres instead of SQLite, as a compose service with a named volume and a pg_dump cron, as this project does.
  • Start-first rollouts. Two app replicas, no container_name, a healthcheck, and Caddy's reverse proxy finds both by DNS. Then a script like rollout.sh. Read this project's with the section 10 diagram next to it.
  • A dev environment. A second compose project on the same VM on another hostname, deployed from a dev branch.
  • Infrastructure as code. One Bicep or Terraform file for the VM and its firewall.
  • Tracing. OpenTelemetry spans per agent turn, to any backend; it is how this project's admin console knows which model and how many tokens.

Costs, roughly

These are ballpark figures to size your expectations; check the provider's current price list. A small VM with 1 vCPU and 1 GB is around ten euros a month, 2 vCPU and 4 GB around thirty to forty. A domain is about ten euros a year. Let's Encrypt certificates are free. GitHub Actions is free for public repositories and has a generous free allowance for private ones. The model calls will cost more than the server.

Beginner mistakes this list is designed to prevent
  • Publishing the database port (5432:5432) "to connect from my laptop". Use ssh -L port forwarding instead.
  • Committing .env. Rotate the key if it ever happens; deleting the file later does not help.
  • Port 22 open to the world with password login enabled. Key only, and your IP only if your provider lets you.
  • No restart policy: the first reboot takes the site down until you notice.
  • No backup, or a backup never restored.
  • Running the app as root in the container.

When something breaks: the order to look

  1. Is the VM up? The Azure portal, or ping / ssh from the VPN. If not, nothing below matters.
  2. Is Docker up? sudo systemctl status docker.
  3. Which container is unhealthy? sudo docker compose ps. Then its logs.
  4. Disk full? df -h. Postgres and Docker both stop writing at 100%.
  5. nginx: docker exec nginx-proxy nginx -t -c /etc/nginx/tcc/nginx-proxy.conf, then its error log.
  6. Certificate expired? openssl s_client -connect chat.tccglobal.com:443 -servername chat.tccglobal.com | openssl x509 -noout -dates.
  7. DNS or firewall? nslookup chat.tccglobal.com; the NSG rules with az network nsg rule list.
  8. Was there a deploy? cat data/ops/deploy.json; the pipeline run's log.
  9. Still lost? The admin console's Status page and docs/monitoring.md's runbooks.

The one idea to keep

Every piece of this platform exists because of a specific thing that went wrong or would have. The backup, the folder ownership, the self-test gate, the canary, the default-deny edge, the fail-closed warehouse client. You do not need any of them on day one. You need the one-line deploy, HTTPS, a health check and an email when it dies, and then the habit of adding the next piece the day you feel its reason.
