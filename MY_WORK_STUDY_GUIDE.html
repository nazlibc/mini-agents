Section 00

/ 00Start here: what you are going to build

My work is the calendar page in agents_and_connectors. You can put your own to-dos on it, or hand a task to an agent, which the server then runs at the time you chose. Around the calendar sit your Azure DevOps tickets, your meetings, a standup summary and your Claude Code sessions. This guide teaches you how every part of it is built, so you could build it yourself.

TL;DR
  • My work is one database table (work_tasks), one module that is allowed to change it (src/work/store.py), and three ways in: the web page, the agents' tools, and a background runner.
  • The hard parts are not the calendar drawing. They are state (who may set a task's status), time (dates, times and time zones), background work (running a task when nobody is watching) and outside systems (Azure DevOps, DevRev, Claude Code), each of which can fail.
  • Every section ends with an exercise that builds the same thing for Ciao Tutor, the example app of your main study guide: a practice planner. The learner plans study tasks, hands some to the tutor agent ("make my lesson at 08:00 every weekday"), and the server runs them. Section 14 is the full build plan (milestones P0 to P8). Your main STUDY_GUIDE.html has a short section that points here.

The one idea

A feature like this is a small state machine with a calendar drawn on top. If the rules about state live in exactly one place and every way in goes through that place, the page, the agents and the background runner can never disagree.

Section 01 · Foundations

/ 01The big picture: one store, three doors

Before any code, get the shape of the system in your head. Everything else in this guide hangs off this one diagram.

TL;DR
  • There are three callers: the page (through HTTP routes), the agents (through tools) and the runner (a background loop). All three call the same functions in store.py.
  • The store checks every input and derives every status. No caller is trusted to set a status itself.
  • Outside systems (Azure DevOps, meetings, Claude Code) sit behind ports: small interfaces, so the calendar does not care which system is behind them.

Three callers, one store. The runner is the only one that runs anything; the store is the only one that decides status.

Why "one store, three doors" matters

Imagine the opposite. The page's route checks that a title is not empty, the agent's tool checks it too but in a slightly different way, and the runner never checks. Six months later, someone changes the rule in one place. Now an agent can create a task the page cannot display. These bugs are slow to find because each piece looks correct on its own.

As a data scientist you already know this problem in another form: training-serving skew. If feature engineering is written twice (once in the training notebook, once in the serving code), the two drift apart. The cure is the same: write the logic once and make every path call it.

In the real code
  • src/work/store.py is sync SQLAlchemy. The routes in src/api/work.py call it, the tools in src/agent/tools_work.py call it, and src/work/runner.py calls it. Read the docstring at the top of store.py: "A task's status is derived here, never set by a caller."
  • Each store function takes user_id and every query filters on it. "Another person's task is never found" is enforced in the SQL itself, not by a check that someone could forget.
  • src/work/__init__.py has the package overview in 10 lines. Read it first when you open the code.

# src/work/store.py
def kind_of(assignee: str) -> str:
    """What a task is by who has it: ``me``, ``agent``, ``routine``,
    ``computer`` or ``claude``."""
    return assignee if assignee in (ME, ROUTINE, COMPUTER, CLAUDE) else "agent"

Notice what is not stored: kind. It is computed every time a task is turned into JSON. If you stored it, you would have two columns that must agree, and one day they would not.

Common misconceptions
  • "The agent runs the task in my browser." No. The browser only saves the task. The backend server runs it, even if your laptop is closed.
  • "A Claude Code task runs on the server." No. The server never runs it. It is a reminder with a copyable command. (This is what confused you on the Azure DevOps ticket earlier.)
  • "The calendar is the feature." The calendar is the easy part. The value is in the rules: who runs what, as whom, when, and what happens if it fails.

Check yourself

Why does the store, not the page, decide a task's status?

Because three callers change tasks. If each one decided status, they would eventually disagree. Putting the rule in the one module everyone must call keeps a single source of truth, the same reason you compute features in one shared function rather than twice.

You give a task to the Monitor agent for tomorrow 09:00 and close your laptop. What happens at 09:00?

The runner loop in the backend (not your browser) finds the task is due, marks it running, runs one Monitor turn as you, writes the answer into a new chat that shows as unread, and marks the task done or failed.

Name the three doors into the store.

The HTTP routes used by the page (src/api/work.py), the agents' tools (src/agent/tools_work.py) and the runner (src/work/runner.py).

/ 02The data model: one row per task

Good features start with a good table. Learn to read each column as a decision: what it means when it is empty, who sets it, and why it exists.

TL;DR
  • One table, work_tasks. Plus work_settings: one JSON blob of settings per person.
  • Empty means something. No date = "no date yet" (the side list). No time = "all day". No run_at = "the server never starts this".
  • Two kinds of column: what the person said (title, date, time, assignee…) and what the system derived or recorded (status, run_at, result, thread_id, done_at…). Callers only send the first kind.

Indexes: designed from the queries

An index is chosen by asking "which queries run often, and what do they filter on?" There are three, one per hot query:

(user_id, date)The page: "this person's tasks between Monday and Sunday"

In the real code
  • The table is WorkTaskModel in src/api/postgres_store.py (SQLAlchemy declarative). Its docstring is a compact summary of the whole feature.
  • Schema changes only add. Columns added after the first release are created on startup with ALTER TABLE work_tasks ADD COLUMN IF NOT EXISTS …. There is no Alembic migration tool. This works because the rule is "never rename or drop a column in place", which also makes zero-downtime deploys safe: old and new code can both run against the same table.
  • Times are stored as naive UTC (datetime without a zone, but always meaning UTC), like the other tables in the app.

Why time is a string and not a SQL TIME

"09:30" is how the page shows it, how the model writes it, and how a person types it. Storing it as text in one fixed format (HH:MM, always two digits) means it sorts correctly as text and never surprises anyone with seconds or time-zone conversions. The store normalises 9:30 to 09:30 on the way in, so the format is guaranteed.

Archive instead of delete

A done task stays on the calendar (struck through) until you archive it. Archiving sets archived_at; nothing is deleted. Why? The standup reads done tasks to tell you what you did since yesterday. If "clean up my list" deleted rows, the standup would lose history. This is called a soft delete: hide the row, keep the fact.

Common mistakes
  • Using one "magic" value for two meanings. If "no time" were stored as 00:00, you could no longer tell "all day" from "midnight". Use NULL and give it one documented meaning.
  • Storing what you can compute. kind is derived from assignee, so it is not a column. status is stored because computing it would need the run history, but only the store may write it.
  • Forgetting the per-user filter. In a multi-user app, every query that reads tasks must say WHERE user_id = ?. One missing filter is a data leak.

Check yourself

A row has date = NULL and time = "10:00". Is that valid?

No. A time needs a date. The store refuses it on create ("A time needs a date.") and on update clears the time when the date is cleared.

Why is there an index on (status, run_at) but no user_id in it?

The runner's query is not per person: it looks for every scheduled task that is due, across all users. So it filters on status and run_at only.

Why does external_id have a unique index?

The hook reports the same Claude Code session many times (after every answer). Unique (user_id, external_id) guarantees one task per session even if two reports race. The code finds the row by it and updates instead of inserting.

Section 03 · Foundations

/ 03The store: validation and a small state machine

store.py is the heart of My work. It is about 1,000 lines, but it does three simple things: it checks input, it derives status, and it only ever touches one person's rows.

TL;DR
  • Every field has a small validator function that either returns a clean value or raises WorkError("why"). A dict maps field name → validator.
  • WorkError becomes HTTP 400 in the routes and "Not added: why" text in the tools. The same message reaches a person and a model.
  • Status follows a state machine. Callers send intentions (done=True, a new date, a new assignee); the store works out the new status.

Validators: one small function per field

# src/work/store.py
class WorkError(ValueError):
    """Input a task does not accept; the message says why."""

def _title(value) -> str:
    title = " ".join(str(value or "").split())
    if not title:
        raise WorkError("A title is required.")
    if len(title) > MAX_TITLE:
        raise WorkError(f"A title is at most {MAX_TITLE} characters.")
    return title

def _time(value) -> str | None:
    """``HH:MM`` from ``H:MM`` or ``HH:MM``; None for all day."""
    text = str(value if value is not None else "").strip()
    if not text:
        return None
    m = _TIME.fullmatch(text)
    if not m or int(m[1]) > 23 or int(m[2]) > 59:
        raise WorkError(f"“{text}” is not a time; use HH:MM, 00:00 to 23:59.")
    return f"{int(m[1]):02d}:{m[2]}"

# What a task's fields are checked with
_FIELDS = {
    "title": _title, "notes": _notes, "date": parse_date, "time": _time,
    "duration": _duration, "tz": _tz, "campaign_id": _campaign_id,
    "campaign_label": _campaign_label, "repeat": _repeat,
    "position": _position, "ado_id": _ado_id,
}

Then create_task runs them all in one line: task = {key: _FIELDS[key](value) for key, value in fields.items()}. After that, it checks the rules that need more than one field ("a time needs a date", "a repeat needs a date").

Notice the error messages. They say what was wrong and what to do: "use HH:MM, 00:00 to 23:59". This matters twice over here, because a model reads these messages too (through the tools). A model that gets "invalid input" is stuck; a model that gets "use YYYY-MM-DD" fixes its call and tries again.

Who may be an assignee

_assignee is the most interesting validator, because whether a value is allowed depends on who is asking:

  • me and routine: always allowed (a routine is checked further by _routine_fields).
  • claude: only if config allows Claude Code for this person (integrations.allowed("claude", user_id)).
  • computer: only if the person connected DevRev with a pasted token.
  • An agent slug: it must be an enabled agent and one this person may use (allowed_agents(user_id)).

This is authorisation inside validation. The page also hides buttons you cannot use, but the server never trusts that. Hiding a button is a convenience; refusing on the server is the security.

The state machine

The caller never writes a status. It sends an intention; the store computes the next state.

Here is the part of update_task that computes the new status. Read it slowly: it is the whole state machine in eight lines.

# src/work/store.py, inside update_task
agent = row.assignee not in LOCAL          # LOCAL = ("me", "claude")
status = row.status
if done is not None:
    status = "done" if done else ("scheduled" if agent else "open")
elif row.assignee != assignee:             # handed to someone else
    status = "scheduled" if agent else "open"
elif agent and moved and status in ("done", "failed"):
    status = "scheduled"                    # moved: it should run again
finished = status == "done" and row.status != "done"
if status != row.status:
    row.status = status
    row.done_at = now if status == "done" else None
row.run_at = _run_at(row.date, row.time, row.tz) if agent else None

And one guard just before it, which prevents a real race:

if row.status == "running" and (moved or done is not None):
    raise WorkError(
        "This task is running now; change when it is or whether it is "
        "done after it has finished."
    )

Why? If you could move a running task to next week, the runner would finish and write "done", and your move would be overwritten by an outcome for a run you no longer wanted. Refusing the change while it runs is simpler than merging two writers.

In the real code
  • _mine(session, user_id, task_id) is the only way update and delete find a row: WHERE id = ? AND user_id = ?. Someone else's task id gives None, which the route turns into 404. The route does not reveal that the task exists.
  • update_task refuses unknown field names: "Cannot change: …". That catches typos from both the page and the model.
  • Every function opens its own Session(db) and commits once. One function = one transaction.
Common mistakes
  • Letting the client send status. Notice that the API's TaskPatch has no status field at all. The page sends done: true.
  • Validating only in the UI. The model, an MCP client or a curl command bypass the UI. Validate on the server, always.
  • Vague errors. "Bad request" helps no one. Each WorkError says what was wrong and the accepted form.

Check yourself

A Monitor task ran and failed. You drag it to tomorrow. What is its status after the drag, and why?

scheduled. It is an agent task (agent is true), its date changed (moved) and its status was failed, so the third branch sets it back to scheduled, and run_at is recomputed for tomorrow.

You tick your own task done. What else can happen in the same transaction?

If it repeats, finished is true, so _add_next adds the next occurrence before the commit (section 09).

Why does the store compute run_at on every update, not just when the date changes?

Because several things change it: date, time, time zone, and the assignee (a task handed from an agent back to "me" must lose its run_at, or the runner would still start it). Recomputing it every time from the current fields is simpler and cannot get out of sync.

Section 04 · Foundations

/ 04Time: dates, clocks and time zones

Every calendar bug you will ever meet is a time bug. My work avoids most of them with one decision: store what the person said (a local day and a local clock time) and compute the exact instant only when the server needs it.

TL;DR
  • A task stores local date + time + the zone tz. The calendar draws exactly those values.
  • For tasks the server runs, the store computes run_at: that local moment converted to UTC. The runner compares run_at with "now in UTC". All day = 09:00.
  • On the page, dates are plain "YYYY-MM-DD" strings, never JavaScript Date objects passed around, so a day can never shift by a time zone.

Two kinds of time

There are two different questions, and mixing them up is the root of most time bugs:

Wall-clock time

"Thursday at 09:00"

What a person means. It depends on where they are. If daylight saving starts, "09:00" is still 09:00 on their wall clock. Store this for anything a human plans.

An instant

"2026-10-15 07:00:00 UTC"

One exact point on the world's timeline. Store this for anything a machine must compare: "is it due yet?", "when did it finish?".

My work stores both, each for its own job. date, time and tz are the wall-clock plan. run_at, created_at, done_at are instants, in UTC.

# src/work/store.py
DEFAULT_RUN_TIME = "09:00"  # when an agent task with a date and no time starts

def _run_at(day: dt.date | None, time: str | None, tz: str) -> datetime | None:
    """When an agent task starts: its local date and time as naive UTC."""
    if day is None:
        return None
    hour, minute = (int(p) for p in (time or DEFAULT_RUN_TIME).split(":"))
    local = datetime(day.year, day.month, day.day, hour, minute, tzinfo=ZoneInfo(tz))
    return local.astimezone(UTC).replace(tzinfo=None)

ZoneInfo("Europe/Amsterdam") knows the daylight-saving rules for every date, so 09:00 in July becomes 07:00 UTC and 09:00 in December becomes 08:00 UTC. You never write those offsets yourself.

Where does the zone come from?

  • From the page: the browser's own zone (Intl.DateTimeFormat().resolvedOptions().timeZone) is sent with every new task, and with an update only when the date or time changes.
  • From an agent's tool call: the zone of the person's most recently changed task; if they have none, work.default_timezone in config.yaml (Europe/Amsterdam).
// chatkit/app/src/work/api.ts
export async function updateTask(id: string, patch: TaskInput): Promise<Task> {
  // The zone goes with a new day or time only: on its own it would move the
  // task (and start a finished agent task again).
  const moved = 'date' in patch || 'time' in patch;
  return json(await apiFetch(`/api/work/tasks/${encodeURIComponent(id)}`, {
    method: 'PATCH', body: JSON.stringify(moved ? { tz: browserTz(), ...patch } : patch),
  }), 'Saving the task');
}

Read that comment twice. Changing tz counts as "moved" in the store (section 03), and moving a done agent task sets it back to scheduled. So if the page sent the zone with every edit, fixing a typo in a finished task's notes from a laptop in another zone would run the task again. A small detail in the client protects a rule on the server.

Dates on the page: strings, not Date objects

// chatkit/app/src/work/dates.ts
/** Local midnight of a YYYY-MM-DD date. */
export function parse(s: string): Date {
  const [y, m, d] = s.split('-').map(Number);
  return new Date(y, m - 1, d);
}
export function addDays(s: string, n: number): string {
  const d = parse(s);
  d.setDate(d.getDate() + n);
  return iso(d);
}

Why not new Date("2026-10-13")? Because JavaScript reads a date-only ISO string as midnight UTC. In Amsterdam that prints as the 13th, but for someone in New York it is the evening of the 12th. Building the date from its parts (new Date(y, m-1, d)) gives local midnight, and keeping strings everywhere else means a task's day is just text that cannot shift.

In the real code
  • dates.ts also does week numbers (ISO 8601), month arithmetic that clamps 31 January + 1 month to 28 February, and the next occurrence of a repeat. It has unit tests in dates.test.ts: date code is exactly where tests pay off most.
  • The server never reads the person's zone from their machine; it only has what the page sent. That is why "the calendar shows a task's date and time as stored" and "the time zone decides only when a handed-over task starts" (docs/work.md).
  • A date already in the past when a task is added starts it at the next pass of the runner. "Now" is not special-cased; "due" simply means run_at <= now.
Common mistakes
  • Storing only UTC for planned events. "Every Monday 09:00" stored as "07:00 UTC" drifts by an hour when daylight saving changes. Store the wall-clock plan plus the zone.
  • Storing a fixed offset (+02:00) instead of a zone name. An offset is a moment's fact, not a place's rule. Europe/Amsterdam is +02:00 in summer and +01:00 in winter.
  • Mixing naive and aware datetimes in Python. Comparing them raises TypeError. The store's rule: naive in the database means UTC; convert at the edges with _naive_utc.
  • Pandas habit: pd.to_datetime with mixed zones quietly gives object dtype or converts to UTC. In app code, be explicit at every boundary.

Check yourself

Each occurrence computes its own run_at from date + 09:00 + zone, so the UTC instant moves from 07:00 to 08:00 and the task still runs at 09:00 on the wall clock.

Why does an all-day agent task need a run_at at all?

The runner only understands instants. "All day" has no start time, so the store picks one (09:00 local). Without it the task would never come due.

Why is tz left out of a PATCH that only changes the title?

Because a zone change counts as moving the task, and moving a done or failed agent task schedules it again.

Section 06 · Running work in the background

/ 06The runner: background jobs without a job queue

How does a task run at 09:00 when nobody has the page open? A loop inside the backend wakes up every minute, finds what is due, and runs it. Simple, but the details (two servers, crashes, shutdowns) are where the engineering is.

TL;DR
  • FastAPI's lifespan starts run_loop as an asyncio task when the server starts, and cancels it when the server stops.
  • Every 60 s a pass: end stale runs, then claim due tasks and start each one in the background, at most 3 at once per process.
  • A claim is an UPDATE … WHERE id = ? AND status = 'scheduled'. Only one server's UPDATE can match, so two servers never run the same task. No locks, no queue.

One pass. Runs are started, not awaited, so a slow agent turn never delays the next pass.

Starting the loop with the server

A lifespan is a function FastAPI runs around the server's life: the code before yield at start-up, the code after it at shutdown. Starting the loop here means "the runner lives exactly as long as the backend process".

The loop and one pass

# src/work/runner.py
INTERVAL_SECONDS = 60
MAX_CONCURRENT = 3
_running: set[asyncio.Task] = set()

async def run_due(store, registry) -> list[asyncio.Task]:
    db = work.engine()
    if db is None:
        return []
    now = datetime.now(UTC)
    await asyncio.to_thread(work.fail_stale, db, now)
    free = MAX_CONCURRENT - len(_running)
    if free <= 0:
        return []
    due = await asyncio.to_thread(work.claim_due, db, now, free)
    return [start(task, store, registry) for task in due]

async def run_loop(store, get_registry) -> None:
    while True:
        try:
            await run_due(store, get_registry())
        except Exception:
            logger.exception("work: a pass over the due tasks failed")
        await asyncio.sleep(INTERVAL_SECONDS)

def start(task: dict, store, registry) -> asyncio.Task:
    run = asyncio.create_task(run_task(task, store, registry))
    _running.add(run)
    run.add_done_callback(_running.discard)
    return run

Four details worth a pause:

  1. asyncio.to_thread. The store is synchronous. Calling it directly from async code would block the event loop (and every HTTP request) while Postgres answers. to_thread runs it in a worker thread and awaits the result.
  2. The try/except around a pass. If one pass fails (database blip), the loop logs it and tries again in a minute. Without it, one exception would silently kill the runner for good.
  3. The _running set. The event loop keeps only a weak reference to tasks made with create_task. If nothing else holds a reference, a running task can be garbage-collected mid-run. Keeping it in a set (and removing it when done) is the documented pattern. It also counts the runs under way for the cap.
  4. Capacity. At most 3 runs per process. What is due beyond that waits for the next pass. Agent turns are expensive (model calls, warehouse queries); a cap protects the server and the model quota.

The claim: safe with two servers

Production runs two replicas of the backend, and each runs this loop. Both may see the same due task at the same moment. The claim makes sure only one runs it:

# src/work/store.py
def _start_run(session: Session, *where) -> bool:
    """Mark the task matching ``where`` as running; whether this call did."""
    taken = session.execute(
        update(WorkTaskModel)
        .where(*where)
        .values(status="running", done_at=None, updated_at=_now())
        .execution_options(synchronize_session=False)
    )
    return taken.rowcount == 1

# in claim_due, for each due id t:
_start_run(session, WorkTaskModel.id == t, WorkTaskModel.status == "scheduled")

The database runs each UPDATE atomically. The first replica's UPDATE changes the row to running and reports rowcount == 1. The second replica's UPDATE finds no row that is still scheduled and reports 0, so it skips the task. This pattern is called a conditional update or compare-and-set, and it is a form of optimistic concurrency: no lock is held; you just make the write conditional on the state you expect.

When things go wrong

What happensWhat the runner does
The agent turn raisesTask failed, error in result, "I could not do this task: …" in the chat
A tool fails inside the turnNot a failure: the agent reports it in its answer; the task is done with that answer
The server stops gracefullyThe run is cancelled; CancelledError is caught, the task is ended as failed ("the server stopped"), and the error is re-raised
The server is killed hardThe task stays running… until any server's next pass sees it has been running over an hour and fails it (fail_stale)

That last row is a nice property of "due = run_at <= now": missed work is never lost, just late. Compare a cron job, which simply does not run if the machine was off at that minute.

In the real code
  • fail_stale uses the same conditional-update trick, so only one replica ends a stale run and adds the next occurrence of a repeating task.
  • "Start now" (store.claim) also uses _start_run, with the condition "not running", so a double click cannot start two runs.
  • The MCP container does not run the loop; only the backend does. One kind of process owns the runner.
Common mistakes
  • "Read, then write" claims. SELECT status, check it in Python, then UPDATE: between the two, the other server does the same. The check must be inside the UPDATE.
  • await-ing each run inside the loop. Then one slow turn delays every other due task. Start runs; do not await them.
  • No stale rule. A process killed mid-run leaves a row running for ever, and nothing can run it again.
  • Reaching for Celery or a message queue first. For a few tasks a minute, a table plus a loop is simpler to run and to debug. A queue earns its place when you need thousands of jobs, retries with back-off, or separate worker machines.

Check yourself

Both issue UPDATE … SET status='running' WHERE id='X' AND status='scheduled'. The database applies one first: its rowcount is 1 and it runs X. The other UPDATE now matches no row (status is no longer scheduled): rowcount 0, so X is not in its claimed list.

Why is the stale limit one hour and not, say, five minutes?

An agent turn or a multi-step routine can legitimately take many minutes. Too short a limit would fail runs that are still working. The limit only needs to catch runs whose server died.

What does asyncio.to_thread protect against here?

Blocking the event loop. The sync database call runs in a thread, so the server keeps answering HTTP requests and other runs keep going while it waits.

Section 07 · Running work in the background

/ 07Handing work to agents: as the person, in a chat

The runner claimed a task. Now what exactly does it do? It runs a normal agent turn, the same code as when you type in the chat, but with no one watching. Three design choices make that safe and useful.

TL;DR
  • As the person. The turn runs under the task owner's user id: their data access, their agents, their tokens. Never as an admin or the server's own identity.
  • Permissions are checked again at run time. A task added last month must not run if the person has since lost access to that agent.
  • In a chat of its own. The task's text becomes the person's message, the answer is added marked unread, and the person can carry on the conversation later.

The prompt the agent receives

/ 08Agents using the calendar: the task tools

"Remind me to call Ghent on Thursday" in any chat puts a task on your calendar. That is the second door into the store: a handful of tools whose docstrings teach the model when and how to use them.

TL;DR

So during a scheduled run the tools still allow reminders for the person (assignee="me") but refuse to hand work to agents, routines or Computer.

/ 09Repeating tasks: one real row at a time

"Every weekday at 08:00" sounds like it needs a recurrence engine. My work does it with one rule: when a repeating task finishes, add the next one.

TL;DR
  • A repeat is one of daily, weekdays, weekly, biweekly, monthly, and needs a date.
  • Only one open task per series exists in the database. When it finishes (ticked, or a run ends done/failed/stale), _add_next copies it to the next date.
  • The page draws the coming dates faded, computed in the browser. They are not tasks yet.

Two ways to model recurrence

Rule-based (iCalendar RRULE)

Store the rule, expand on read

One row: "FREQ=WEEKLY;BYDAY=MO". To show next month, expand it. Exceptions ("skip 25 Dec", "move this one") need extra tables. Powerful, complex.

Materialise next (My work)

One real row; make the next on finish

Each occurrence is a normal task with its own status, result and chat. Moving one moves only that one. Simple, and every occurrence can run, fail and be retried on its own.

For a calendar where occurrences run and have outcomes, the second fits much better: the runner never needs to know about rules, it only sees ordinary scheduled tasks.

# src/work/store.py
def next_occurrence(day, repeat, after=None):
    def step(d):
        if repeat == "monthly":
            year, month = d.year + d.month // 12, d.month % 12 + 1
            return dt.date(year, month, min(d.day, calendar.monthrange(year, month)[1]))
        d += timedelta(days={"weekly": 7, "biweekly": 14}.get(repeat, 1))
        while repeat == "weekdays" and d.weekday() > 4:
            d += timedelta(days=1)
        return d
    nxt = step(day)
    while after is not None and nxt <= after:   # never come back in the past
        nxt = step(nxt)
    return nxt

Two subtle rules are in here. Monthly clamps: 31 January → 28 February → 28 March (it keeps the clamped day from then on, as the doc says). after = today: if a daily task was ticked three days late, the next one is tomorrow, not the day after the old date, which is already in the past.

One open task per series

def _add_next(session, done):
    if not done.repeat or done.date is None:
        return
    series = done.series_id = done.series_id or done.id
    if session.execute(select(WorkTaskModel.id).where(
            WorkTaskModel.user_id == done.user_id,
            WorkTaskModel.series_id == series,
            WorkTaskModel.status.in_(OPEN_STATES),       # open, scheduled, running
            WorkTaskModel.id != done.id).limit(1)).first():
        return                                          # the series already has a next one
    today = datetime.now(ZoneInfo(done.tz)).date()
    day = next_occurrence(done.date, done.repeat, today)
    session.add(WorkTaskModel(... a copy with date=day, series_id=series,
                              status="scheduled" or "open", run_at=...))

Why the "already has an open one" check? Tick a daily task done, untick it, tick it again: without the check you would get two "tomorrows". The check makes _add_next idempotent per series: calling it twice has the same effect as once. Idempotency is the single most useful property for anything that may be retried or raced, in apps and in data pipelines alike.

Common mistakes
  • Creating a year of rows up front. Then changing the time of "every Monday" means updating 52 rows, and deleting the series is a bulk operation.
  • A repeat is not a retry. A failed run still brings the next occurrence; the failed one stays failed until moved or run again.

Section 10 · Outside systems

/ 10Ports and adapters: Azure DevOps, meetings, Claude Code

The calendar talks to three outside systems. Each can be slow, down, or not available to this person. The design question is: how do you add them without the core code knowing or caring?

TL;DR
  • A port is an interface the core defines: "what I need from a work item system" (WorkItemSource), "what I need from a calendar" (CalendarSource). An adapter implements it for one real system.
  • integrations.sources_for(user_id) is the one door: it hands back the adapters this person may use, or None. Config decides who gets what.
  • Failures are typed (SourceUnavailableError, NotYoursError, NoSuchItemError) and mapped to HTTP codes in one place. Reads degrade (200 with an error field) instead of failing the page.

The idea: hexagonal architecture

Also called ports and adapters. The core (store, standup, routes) depends only on small interfaces. The messy specifics (Azure DevOps's WIQL, DevRev's API) live in adapters at the edge. You can swap Azure DevOps for Jira by writing one new adapter, and you can test the core with a fake adapter that needs no network.

# src/work/ports.py (trimmed)

Who gets which system

Azure DevOps: writing with the platform's identity, safely

There is no per-person Azure DevOps token. The server's own identity (the VM's managed identity on dev and prod, your az login on a laptop) reads and writes. That is powerful, so the adapter adds three protections:

  1. "Me" is never what the request says. It is the signed-in email, or work.ado.me for the local dev user. That is the error you hit earlier: without work.ado.me the adapter does not know who you are, so it refuses (SourceUnavailableError) rather than guess.
  2. Only your own items change. An item must be assigned to you or created by you, or the write raises NotYoursError (403).
  3. Every write leaves a comment on the item: Changed in My work by <email>: …, because Azure DevOps itself will show the platform identity as the author. This is an audit trail.

Query injection, the WIQL edition

Azure DevOps is queried with WIQL, a SQL-like language. A person's view has a project name, team name and states they type. If those went into the query as text, a state named x') OR ([System.Id] > 0 would rewrite the query: the same attack as SQL injection. The defence is in two layers:

# src/work/adapters/ado.py
_NAME = re.compile(r"\w[\w .&()-]{0,62}")   # names: letters, digits, spaces, . & ( ) -

def _q(text) -> str:
    """A WIQL string literal."""
    return "'" + str(text).replace("'", "''") + "'"

First an allowlist: a name with quotes or brackets is refused before it is saved. Then quoting: every value is a properly escaped string literal. The sprint and project use WIQL macros (@CurrentIteration, @project) instead of text. Use parameters when the query language has them; when it does not, validate and quote.

Meetings: a heuristic, isolated in its adapter

Meetings come from DevRev, which mirrors your Outlook. DevRev keeps cancelled meetings and, when a meeting moves, sometimes keeps the old copy too. _current() in devrev_meetings.py cleans that up with rules (drop cancelled; within a title, keep the last-changed copy per day; drop a stale copy close to a fresh one in a weekly series). It reads three weeks either side of what you asked so it can see the rhythm of a series. Messy, but it is all inside the adapter: no other file knows DevRev has this quirk.

Pointer events

Resizing, drawing a new task

pointerdown → listen to pointermove → pointerup. Needed when you want continuous feedback (the edge follows the mouse in 15-minute steps).

Pixels become minutes: an hour is 48 px tall, so minutes = (y - top) / 48 * 60, then snap(minutes, 15) rounds to a quarter hour.

Your own order: fractional positions

// order.ts: the position between the neighbours where a task is dropped
if (prev && next) return ((prev.position ?? 0) + (next.position ?? 0)) / 2;
if (prev) return (prev.position ?? 0) + 1;
return (next?.position ?? 0) - 1;

Drop a task between positions 2 and 3 and it gets 2.5. Only the moved task is updated: one PATCH, not a renumbering of the whole list. This is called fractional indexing. (With floats you can halve about 50 times between the same two neighbours before precision runs out; for a person's to-do list that is plenty.)

Overlapping tasks side by side

layout.ts sorts the day's timed tasks by start, gives each the first column that is free at its start, and groups tasks that overlap so every member of a group gets the same width. It is the classic interval partitioning greedy algorithm, in 35 lines, with no React.

Hide what is not yours

On load, the page calls GET /api/work/capabilities once: {computer, meetings, work_items, claude}. Each false hides a button or section. Remember: hiding is for clarity; the server still refuses (section 03).

  • View, filters, side panel and tab are remembered in localStorage, always inside try/catch (private windows throw).
  • The card saves most fields as soon as they change, but the title and notes only when the card closes, so you do not send a PATCH per key press.
  • Every screen follows docs/ui_principles.md: no explanation text on the page, icons with tooltips, no dead ends. Read it before you change any UI in the real app.
Common mistakes
  • Optimistic without rollback. If the server refuses and the screen keeps the change, the page lies until the next reload.
  • Intervals without cleanup. Each re-render adds a timer; after a minute you poll ten times a second.
  • Inserting model or user text with innerHTML. A task title like <img onerror=…> runs code. Use textContent (React escapes for you).

Why poll every 10 seconds only while something is running?

That is when an outcome is about to change. The rest of the time a minute is fresh enough, and slower polling costs the server less.

What to learn next

Important next

  1. Database transactions and isolation levels (search: "PostgreSQL transaction isolation read committed"). Section 06's claim works because of how one UPDATE is isolated; knowing why makes you safe with any shared state.
  2. Idempotency and at-least-once execution (search: "idempotency key", "at-least-once vs exactly-once"). The same idea governs retries in data pipelines, APIs and job runners.
  3. asyncio properly: event loop, tasks, cancellation, to_thread. The Python docs' "Coroutines and Tasks" page, then "Developing with asyncio".
  4. Hexagonal architecture (Alistair Cockburn's original article, "Hexagonal architecture"). A short read that will change how you structure every integration.

Interesting but optional

  • iCalendar RRULE (RFC 5545) and dateutil.rrule, to compare with the "materialise next" approach.
  • Fractional indexing with strings (Figma's and Evan Wallace's write-ups) for orders that never run out of precision.
  • Job queues (Celery, RQ, Postgres SELECT … FOR UPDATE SKIP LOCKED) to see what the next step up from a polling loop looks like.
  • Server-sent events or WebSockets instead of polling, which your mini-agents chat already uses for streaming.
The one idea, again
