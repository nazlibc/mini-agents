/ 01The one idea everything hangs on

Thesis

In this codebase, an agent is not a class hierarchy — it's a system prompt + a list of tool names + a model choice, fed into one generic loop that alternates between “ask the LLM” and “run the tools it asked for.” Fourteen agents, routing, streaming, connectors — all of it is layered on top of a core you can write in ~50 lines. Your replica makes that core visible.

That core decomposes into six concepts. Every milestone below teaches exactly one or two of them:

1

Agent = data, not code

src/agent/definitions/a03_forecasting.py

An AgentDefinition dataclass: id, name, description, system_prompt, tool_names, model. No subclasses — a new agent is a new data file.

2

One generic loop drives all agents

src/agent/base.py

BaseAgent: a 2-node graph — call the LLM; if the reply contains tool calls, execute them and loop back; otherwise return the answer.

3

Tools live in a registry

src/agent/tools/__init__.py

@tool-decorated functions in a TOOL_REGISTRY dict; get_tools_by_name() hands each agent only its declared subset.

4

A registry + factory assemble live agents

src/agent/registry.py · src/config.py

create_llm(profile) hides the provider; the registry filters tools, picks the LLM, builds and caches the agent instance.

5

Routing is one cheap LLM call

src/agent/router.py

AUTO mode = list every agent's description, ask a small model “which id?”, regex-extract the answer, never raise — fall back to the previous agent.

6

Streaming is events, not magic

src/api/chat_routes.py · chatkit/app/src/chat/useChatStream.ts

The agent yields (thinking | tool_call | tool_result | response) tuples → mapped to SSE events → the browser applies them to the page as they arrive.

M1a

The raw ReAct loop — the heart

✓ DONE ~1 session
Concept

Tool calling demystified: the LLM never runs anything. When you “give” it tools, you're really sending it a list of function signatures. If it decides one is needed, its reply contains no text — just a structured request:

AIMessage(
    content="",
    tool_calls=[{ "name": "get_campaign_stats",
                  "args": {"campaign_id": "C001"},
                  "id":   "call_abc123" }]
)

Your code looks up the function, runs it, appends the result as a ToolMessage (tagged with that same id), and calls the LLM again — now it can see the data and answer. That's the whole secret. The loop is ~40 lines.

M1b

Same loop, now in LangGraph

✓ DONE ~1 session
Concept

LangGraph doesn't add intelligence — it gives your loop a shape: named nodes, explicit edges, and a state object the framework carries between them. Your while True becomes a graph; your messages.append(...) becomes a reducer. Nothing about the behaviour changes — that's the point, and seeing it is the lesson.

You'll also restructure run_agent into a generator that yields progress events. That generator becomes your streaming contract: in M3 each yielded tuple maps 1:1 to an SSE event the browser receives.

Walkthrough

  1. Meet the state object

    Add to the top of src/agents/base.py (keep your run_agent — you'll want it for comparison):

    from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]

    Complete as given. What it means: a LangGraph graph passes a state dict from node to node. Each node returns a partial update (just the new messages), and the add_messages annotation is the reducer — the rule for merging updates into state. It appends. In M1a, messages.append(reply) was your state management; this line is the same thing, made declarative so the framework can stream and checkpoint it.

    ▸ show the code + why 
        def stream_chat(self, user_text: str):
        state = {"messages": [HumanMessage(user_text)]}
        for update in self.graph.stream(state, stream_mode="updates"):
            for node_name, node_out in update.items():
                for msg in node_out["messages"]:
                    if isinstance(msg, ToolMessage):
                        yield ("tool_result", msg.content)
                    elif msg.tool_calls:
                        for call in msg.tool_calls:
                            yield ("tool_call", {"name": call["name"], "args": call["args"]})
                    else:
                        yield ("response", msg.content)

M2

Many agents, one router

✓ DONE ~1 session
Concept

Scaling from one agent to N is a data problem, not a code problem. And “AI routing” is unglamorous: one cheap LLM call over the agents' description fields, a regex to extract the id, and a fallback so it never crashes. That description field you've been carrying since M1a? This is why it exists.

Design rule you'll feel here: the router must never raise. A wrong agent is a recoverable annoyance; a crashed router kills the chat. The original's classify_agent is wrapped in fallbacks for exactly this reason.

Walkthrough

M3

FastAPI + SSE streaming

✓ DONE ~1 session
Concept

Streaming here is events, not tokens: your M1b generator tuples map 1:1 to Server-Sent Events. SSE is just a long-lived HTTP response whose body arrives in chunks, each chunk formatted as:

event: tool_call
data: {"name": "get_campaign_stats", "args": {"campaign_id": "C003"}}
← a blank line terminates each event — the double newline IS the protocol

That's the whole protocol — plain text over plain HTTP. No websockets needed: chat responses only flow server→client, and SSE does exactly that with none of the connection ceremony. The server stays stateless for now: one request in, one event stream out, nothing remembered (sessions are M5's problem).

A chat page — plain HTML & JavaScript

← IN PROGRESS ~1 session
Concept

No React, no npm, no build step. One HTML file, served by the FastAPI server you already have. Same move as M1: hand-write it first, meet the framework afterwards — M4b does the identical thing in React, and it makes far more sense once you've done it yourself.

If frontend is new, here is the entire mental model. A web page is a tree of elements (the DOM). JavaScript running on that page can do three things: find an element, change it, and react to events (“run this function when the form is submitted”). That's it. There is no magic — you'll write about 40 lines of JavaScript and every one of them does one of those three things.

The one genuinely tricky part is the same as on the server: the network doesn't respect your event boundaries. fetch hands you arbitrary byte chunks — one read might contain two-and-a-half SSE events. So you keep a buffer, split on the blank line (\n\n) that ends an event, and leave the incomplete tail for the next read.

  4. The hook that owns chat state

    web-react/src/useChatStream.ts 
    import { useState } from "react";
import { parseSSEStream } from "./sseParser";

  role: "user" | "assistant";
  text: string;
  tools: string[];      // tool calls made while answering
  agent?: string;       // which agent answered
};

export function useChatStream() {
  const [messages, setMessages] = useState<Msg[]>([]);
  const [busy, setBusy] = useState(false);

  async function send(text: string, agent: string) {
    setBusy(true);
    setMessages(m => [...m,
      { role: "user", text, tools: [] },
      { role: "assistant", text: "", tools: [] },   // placeholder we fill in
    ]);

    // helper: replace the last message using an updater function
    const patch = (fn: (m: Msg) => Msg) =>
      setMessages(ms => ms.map((m, i) => (i === ms.length - 1 ? fn(m) : m)));

    try {

        method: "POST",
        headers: { "Content-Type": "application/json" },

After M0 — setup & the LLM factory

Your hello.py never mentions an API key. Trace how the key gets from your disk into the request to OpenAI.

load_dotenv() doesn't hand the key to anything — it copies the contents of .env into the process's environment variables. Separately, ChatOpenAI looks up os.environ["OPENAI_API_KEY"] when it's constructed, because that name is its convention.

Two parties that never talk to each other, meeting at the environment. That's why the debug check when auth fails is print(os.environ.get("OPENAI_API_KEY")) — you're inspecting the meeting point.

If create_llm("claude-sonnet") returned an Anthropic model instead, why would nothing else in the project need to change?

Adding the key to .env and editing the factory is the mechanical part. The reason nothing else changes is the interface: ChatOpenAI and ChatAnthropic both implement the same LangChain chat-model interface, and every caller in your project only ever uses .invoke() and .bind_tools() — which both provide.

If the two classes had different method names, the factory wouldn't save you at all.

Program against the interface, hide the implementation in one place. It's why the original repo swaps between GPT and Claude per agent without any agent code knowing.

After M1a — the raw ReAct loop

What breaks if you append the ToolMessages but forget to append reply — the AI message carrying the tool_calls?

Not a Python error in your code. The next invoke sends a conversation containing ToolMessages that answer a request which isn't there, and the OpenAI API rejects it with a 400: the protocol requires every ToolMessage to follow an AIMessage whose tool_calls carry the matching ids.

The pairing you built with tool_call_id is two-sided: results must point at requests, and the requests must be present. That's why the original persists complete message histories, never just the “useful” parts.

Your answers came back as markdown with bold and lists. Which component produced that formatting — your tools, your loop, or the model?

The model. Your tools returned plain strings like C001: Summer Stamps, and your loop only moves messages around — it has no formatting logic anywhere. The model composed the final answer and chose to emit **C001** and numbered lists.

Proof you already had: the terminal shows raw asterisks, because nothing in your stack renders markdown. Rendering is the frontend's job (M4).

Knowing who produces formatting versus who renders it is exactly the seam between backend and frontend.

After M1b — the LangGraph swap

In agent_node you prepend a SystemMessage when msgs[0] isn't one. Does that SystemMessage ever get stored in graph state?

No — never. Look at what the node returns: {"messages": [reply]}, just the reply. Your prepended list msgs = [SystemMessage(...)] + msgs is a local variable used for the invoke call and then discarded.

So in the persisted state, msgs[0] is always the HumanMessage, the isinstance check is always False, and a fresh SystemMessage is re-prepended locally on every iteration. It works — but not for the reason it looks like.

See it yourself: add print(type(state["messages"][0]).__name__) at the top of agent_node and watch it print HumanMessage every round.

So when does the check ever matter? When stored history is loaded into state with the system prompt already in it — that's M5.

What if the node returned {"messages": [SystemMessage(...), reply]} instead? Trace the state over two iterations.

With add_messages, whatever a node returns is appended to the end of state. Always. There is no “insert at the front”:

state at start:        [Human]

iteration 1
  node returns:        [Sys, AI₁]           ← appended
  state is now:        [Human, Sys, AI₁]
  ToolNode appends:    [Human, Sys, AI₁, Tool₁]

iteration 2
  check reads state[0] → Human, NOT a SystemMessage
  so it prepends ANOTHER Sys locally, returns [Sys, AI₂]  ← appended
  state is now:        [Human, Sys, AI₁, Tool₁, Sys, AI₂]

Two problems. The check can never save you — appending can't change state[0], so every iteration adds one more system prompt. And they land in the wrong place: a system prompt's job is to be first, framing everything after it. Buried mid-conversation it's wasted tokens at best, and at worst the model reads it as a mid-chat instruction change.

A node's return value is not “the new state,” it's an instruction to the reducer — and with add_messages, that instruction is only ever “append these.”

After M2 — registry & router

Your registry caches one BaseAgent per agent id, shared across every question. Does anything leak from question 1 into question 2?

No. The cached object holds only reusable machinery: the definition, the bound LLM client, the compiled graph — none of which changes per question. Conversation state lives in the state dict, and stream_chat builds a fresh one on every call:

state = {"messages": [HumanMessage(user_text)]}

That dict is created, flows through the graph, and is discarded when the generator finishes. This is why caching is safe here — and would have been a disaster if you'd stored messages on self. It's also why your agents are currently amnesiac between questions.

The object is shared; the conversation is not. In M5, adding memory means loading history into that state dict, never onto the cached object.

classify_agent swallows every exception. If your OpenAI key expired, what would a user experience — and is that the right behaviour?

Trace it: the router raises on the auth failure, swallows it, and returns fallback — so routing quietly degrades to “always A01” with no signal. Then stream_chat hits the same expired key, but nothing catches it there, so it surfaces as your error event.

The user does see a real error, so the system isn't lying to them. But you have lost the diagnosis: the error says “auth failed during chat,” and nothing tells you routing has been broken for every request.

The swallow is right; the silence is wrong. Best-effort routing with a sticky fallback is genuinely correct — a mis-routed answer beats a dead chat. But except Exception: pass discards the evidence. One-line fix: logger.warning("router failed, using %s", fallback, exc_info=True) before falling back. That's what the original does — degrade silently to the user, loudly to the operator.

“Swallow the exception” and “discard the information” are separate decisions. Conflating them is one of the most common ways production systems become undebuggable.

After M3 — the API layer

Validating the agent id: does that check belong in chat.py or registry.py?

registry.py — it's the single door between “agent as data” and “agent as running object,” and your CLI goes through it too. Validate there and every caller gets the same clear failure for free; validate in chat.py and the CLI still raises a bare KeyError, with the check duplicated for each new entry point.

Validate where the knowledge lives. registry.py is the only module that knows what a valid agent id is.

Why must the agent event be emitted after get_agent(), not before?

Because a bad id would otherwise announce a nonexistent agent first and fail second — a client would have already updated its dropdown before the error arrived.

There's a deeper constraint underneath: you can't send an HTTP 500 once streaming has started — the 200 status line already went out. Errors have to travel inside the stream as an error event, which means anything that can fail cheaply should fail before you commit to the stream's narrative.
